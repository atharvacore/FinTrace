# Known Limitations

FinTrace is a portfolio prototype. It is **not** production-ready, **not** regulatory-certified and
**not** validated for real anti-money-laundering (AML) decisions. This page lists what it does not
do, so nobody mistakes it for more than it is.

## Data and labels

- **Synthetic data only.** The model is trained on PaySim, a simulator. The bundled sample in
  `data/sample/` is generated by `scripts/generate_sample_data.py` and is even simpler.
- **Fraud is not money laundering.** PaySim's `isFraud` marks simulated account-takeover fraud.
  FinTrace treats it as a stand-in label for "worth a look", never as confirmed laundering.
- **The headline score is a simulator signature.** In PaySim, a TRANSFER or CASH_OUT for exactly
  the full balance is always fraud and never legitimate. The deployed model's 0.9999 average
  precision mostly measures that quirk. Without balance features the same model reaches 0.629
  ([MODEL_REPORT.md](MODEL_REPORT.md)). Real payment fraud would not look like this.
- **Scores are saturated.** Because of that signature, nearly every flagged PaySim transaction
  scores between 0.997 and 1.0. The score alone cannot rank alerts, which is why priority also
  counts how many monitoring rules agree (ADR-020).
- PaySim has no customer profiles, devices, locations, counterparty networks or sanctions data,
  which real monitoring depends on.

## Detection

- Four simple monitoring rules (large amount, account drain, new destination, velocity). Real
  programmes run hundreds of tuned scenarios.
- No network or graph analysis (mule rings, layering chains, shared counterparties).
- No sanctions or PEP screening, no customer risk rating, no KYC.
- Scoring is batch or on demand, not real-time streaming.
- No drift monitoring, no scheduled retraining, no champion/challenger comparison.
- No per-alert explanations beyond reason codes and rule hits (no SHAP or similar).

## Workflow and compliance

- No regulatory reporting (no SAR/STR filing). "Escalate for reporting" is only a recorded
  decision.
- No four-eyes approval beyond "a senior analyst closes cases", no SLA timers, no case
  attachments.
- Uploads through the dashboard are capped at 50 MB; the full PaySim file goes through the CLI.
- The audit log is append-only by design in the application, but the database does not stop a
  database administrator from editing it.

## Security and operations

- Single tenant. Access tokens live in the browser tab's `sessionStorage` and cannot be revoked
  before they expire (default 60 minutes). No refresh tokens, MFA or SSO.
- No rate limiting on login.
- The Compose stack is for one machine: ports bind to `127.0.0.1`, there is no TLS, and secrets
  come from a local `.env` file. Running it on a server would need TLS, a secrets manager,
  backups and monitoring first.
- Tested on Linux containers and in GitHub Actions. Commands for Windows PowerShell are written
  out in the README, but this project was not run on a Windows machine during development.

## Evaluation

- One chronological split of one dataset. No confidence intervals, no repeated backtests.
- "Alerts per 1,000 transactions" is the only workload measure; real teams also track time to
  close and how many alerts each analyst can handle.
